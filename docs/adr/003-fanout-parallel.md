# ADR-003: Fan-out подзадач — split/join только для read-only веток

- Статус: accepted
- Дата: 2026-08-17
- Связанные решения: D-30 (без worktree), D-33 (пул процессов), T-28
- Реализация: `internal/service/runsmachine/action.go` (parallelGroupAction)

## Контекст

Нужны параллельные ветки пайплайна (fan-out): независимые исследования/
планирование подзадач, затем join. Главный открытый вопрос T-28 — git:
параллельные пишущие этапы в одном чекауте конфликтуют; worktree
запрещены (D-30), а мерж-автоматика противоречит D-32 (пайплайн не
коммитит).

## Решение

- Спека: этап получает `parallel_group` + `read_only: true`; группа
  объявляется в `parallel_groups` с политикой `on_failure: fail_fast |
  wait_all`. Динамического fan-out (список от LLM) НЕТ — ветки статичны
  в пайплайне (риск неконтролируемого роста).
- **Параллелятся только read-only этапы** (исследования, анализы,
  планирование). Валидация блокирующая: этап в parallel_group без
  read_only не сохраняется. Это конвенция (harness yolo — ядро не
  контролирует его файловые операции), как и «не коммитить» (D-32);
  принудительной изоляции нет — осознанно.
- Семантика join: все ветки succeeded/skipped → движение дальше.
  fail_fast: первая failed → ран failed сразу. wait_all: дождаться
  остальных веток → failed.
- Auto-resume/interrupted работают на уровне отдельной ветки (общий
  контур D-14), параллелизм — за счёт пула процессов T-09 (семафор).
- Пишущие этапы (кодинг, fixer) остаются ЛИНЕЙНЫМИ.

## Последствия

- (+) Параллельный ресёрч без git-конфликтов; движок остаётся
  линейным по хранению (та же run_stages, события, CAS).
- (−) Полноценный параллельный кодинг невозможен до решения worktree/
  мержа (если понадобится — отдельный ADR с пересмотром D-30).

## Альтернативы

- **Worktree per branch + merge** — отклонено: прямое нарушение D-30 и
  D-32 (мерж = запись в чекаут/коммиты).
- **Динамический fan-out от LLM** — отклонено для первой версии:
  неконтролируемый рост процессов/расхода; статические ветки решают
  главный кейс BRAINSTORM.
