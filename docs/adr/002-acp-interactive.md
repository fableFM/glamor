# ADR-002: Интерактивный диалог с пользователем — ACP vs «вопросы как артефакт»

- Статус: proposed
- Дата: 2026-08-17
- Связанные решения: D-15 (recovery), D-20 (вопросы как артефакт), ADR-001
- Эксперимент: T-27, спайк `backend/cmd/acp-spike/main.go`

## Контекст

Сейчас диалог «этап ↔ пользователь» реализован по D-20: этап пишет
`questions.md` и завершается → гейт `question` → ответ пользователя →
resume сессии новым процессом (`kimi -S <id> -p "…"`). Каждый вопрос —
это полный ping-pong: завершение процесса, гейт, спавн нового процесса,
перезагрузка контекста сессии.

T-27 проверяет альтернативу: живой двусторонний протокол ACP
(Agent Client Protocol, https://agentclientprotocol.com) поверх stdio —
сессия живёт в long-lived процессе, вопросы/ответы идут без рестарта,
Interrupt & Steer — через `session/cancel` без убийства процесса.

### Результаты спайка (2026-08-17, kimi 0.36.0, `go run ./cmd/acp-spike`)

Прогон: initialize → session/new → один промпт «Ответь одним словом: ок»
(один LLM-вызов, как разрешено T-27) → чтение стрима → завершение.

### Факты протокола (спека v1 + подтверждено спайком)

- **Фрейминг — NDJSON, не LSP**: одно JSON-RPC 2.0 сообщение на строку,
  разделитель `\n`, встроенные `\n` запрещены; заголовков Content-Length
  НЕТ (protocol/v1/transports). Чтение — обычный line-scanner.
- **Handshake дешёвый**: initialize + session/new ≈ 0.5–0.6 c суммарно
  (спавн процесса включительно).
- **Двусторонность**: агент шлёт клиенту запросы
  (`session/request_permission`, `fs/*`, `terminal/*`) — клиент ОБЯЗАН
  отвечать, иначе ход повиснет. Клиентские capabilities опциональны;
  опущенная = unsupported (спайк не объявлял fs/terminal — запросов
  не было; пермишенов на промпте без tool calls тоже).
- **Стрим событий**: `session/update` с подтипами `agent_message_chunk`,
  `agent_thought_chunk`, `plan`, `tool_call`, `tool_call_update`,
  `usage_update`, … — готовая нормализованная схема (ср. ручную
  нормализацию NDJSON-стримов в harness-матрице).
- **Отмена**: `session/cancel` (нотификация) → агент обязан ответить на
  pending `session/prompt` со `stopReason="cancelled"` (не ошибкой).
- **Идемпотентности нет**: в протоколе нет idempotency-ключей;
  `session/new` не идемпотентен (каждый вызов = новая сессия). Дедупликация
  повторов — забота клиента (в glamor это уже решено на уровне гейтов/БД,
  D-12).
- **Обрыв**: живой ACP-процесс НЕ переживает рестарт клиента (демона) —
  stdio-пайпы умирают вместе с родителем. Восстановление — только из
  нового процесса: `session/load` (реплей истории нотификациями) или
  `session/resume` (без реплея). kimi рекламирует оба + `fork` + `list` +
  `delete` + `close` — самое богатое sessionCapabilities из матрицы.
- **Аутентификация**: kimi рекламирует `authMethods` (1 метод); для
  локального запуска не потребовалась, но клиент обязан уметь ветку
  `authenticate`.
- **Мелочь-наблюдение**: `usage_update` пришёл после ответа на
  `session/prompt` — учёт usage нельзя жёстко привязывать к границе хода.

## Решение

**Гибрид (вариант В) как целевая модель; по умолчанию остаёмся на А.**
Пайплайн-нода получает опциональный флаг `interactive: true`; supervisor
умеет оба режима. Реализация интерактивного режима — отдельной задачей
после M4, когда появится конкретный этап с плотным диалогом (кандидат —
интервью/сбор-требований). До тех пор все этапы работают по D-20.

```
                         interactive: false (дефолт)     interactive: true
                         ─────────────────────────       ─────────────────────────
  Транспорт              одноразовый процесс,            long-lived `kimi acp`
                         resume через `-S <id> -p`       (NDJSON JSON-RPC stdio)
  Вопрос пользователю    questions.md → gate →           session/prompt ход,
                         resume новым процессом          request_permission/текст
  Ответ                  новый процесс (~overhead        тот же процесс, новый
                         0.6–3 c спавн+загрузка          prompt (~0 overhead,
                         контекста + полный LLM-ход)     только LLM-латентность)
  Interrupt & Steer      SIGTERM → interrupted →         session/cancel без
                         auto-resume (новая строка)      убийства процесса
  Recovery (D-15)        штатно: процесс не нужен        процесс мёртв → degrade
                         живым                           в режим А (см. ниже)
  Harness-покрытие       все 6 harness'ов                kimi, opencode нативно;
                                                         qwen experimental;
                                                         claude/codex — внешние
                                                         адаптеры; pi — никогда
```

### Совместимость с D-15 (recovery)

Живой ACP-процесс не переживает рестарт демона — это фундаментально
(stdio-пайпы). Поэтому для interactive-стадии startup-recovery работает
так же, как сейчас: running-стадия-сирота → `interrupted` → auto-resume,
но **resume интерактивной стадии выполняется в режиме А** (одноразовый
процесс + `session/load`-эквивалент через нативный resume `-S <id>`).
То есть интерактивность — свойство живого демона, а не персистентного
состояния; источником истины остаётся SQLite/артефакты. Открытый вопрос
на момент рестарта гарантированно не теряется: он либо уже записан
артефактом/гейтом (режим А), либо его повторит новый ход после resume —
для этого interactive-этап ОБЯЗАН дублировать каждый заданный вопрос в
журнал/артефакт (принцип D-20 сохраняется как аудит-слой).

### Измеримое сравнение (факты спайка + матрица)

- **Время ответа на вопрос.** А: спавн+handshake ≈ 0.5–0.6 c (измерено:
  initialize 429 мс + session/new 115 мс) + загрузка контекста сессии
  нативным resume + полный LLM-ход; вопрос/ответ через гейт — секунды–
  минуты ожидания пользователя + этот overhead на КАЖДЫЙ вопрос.
  Б/В: живой `session/prompt` — нулевой процессный overhead, только
  LLM-латентность (в спайке весь ход 8.97 c — это чистое время модели;
  delta-стрим приходит с TTFT ~8 c до первого chunk'а, чанки идут
  пачками по ~0.1–0.2 c). При плотном диалоге (5–10 вопросов подряд)
  гибрид экономит 5–10 × (спавн + загрузка контекста) и убирает
  gate-resume-церемонию.
- **Сложность ядра.** Спайк — ~300 строк stdlib-only. В ядре добавится:
  NDJSON-фрейминг + id-корреляция (тривиально), обработчики
  agent→client запросов (permission ↔ гейт: нетривиально, нужен маппинг
  options→resolve), cancel-семантика, watchdog живого процесса,
  ветка recovery «interactive → degrade в А». Оценка: +600…900 строк
  в supervisor/harness против неизменного контура А. Стейт-машина
  (ADR-001) НЕ меняется: события и гейты остаются теми же.
- **Сценарии отказа.** А: сбой процесса = штатный путь (interrupted →
  resume), вопрос не теряется никогда (он — артефакт). Б/В: сбой демона
  посреди незаписанного диалога теряет «полёт» разговора (не зафиксированные
  в артефакте уточнения); лечится обязательным дублированием вопросов в
  журнал + degrade-resume. Сбой самого ACP-процесса (крах kimi) —
  симметричен А: interrupted → resume, session/load реплеит историю
  (kimi поддерживает, подтверждено capabilities).

## Последствия

- (+) Для этапов с плотным диалогом — диалог без рестартов: секунды вместо
  «гейт + resume + новый процесс» на каждый вопрос; Interrupt & Steer без
  убийства процесса (`session/cancel`).
- (+) ACP даёт готовую нормализованную схему событий (chunk'и текста,
  thinking, plan, tool_call, usage) — для kimi/opencode отпадает ручной
  парсинг нативных NDJSON-стримов.
- (+) Решение обратимо: `interactive: false` остаётся дефолтом, контур А
  не трогаем, стейт-машина и D-15 не меняются.
- (−) Второй транспорт в supervisor'е: NDJSON-клиент, permission-бридж
  agent→client запросов в гейты, cancel-семантика, watchdog long-lived
  процесса — постоянная цена поддержки.
- (−) Покрытие harness'ов неполное (матрица, риск 9): kimi/opencode —
  нативно, qwen — experimental (и несовместим с `--json-schema`),
  claude/codex — только внешние npm-адаптеры, pi — никогда. ACP не может
  быть ЕДИНЫМ транспортом — только опциональным.
- (−) Интерактивность не переживает рестарт демона: после recovery стадия
  продолжается в режиме А. Пользователь, ожидающий «живого» диалога, после
  рестарта получает артефактный — это надо явно показывать в UI.
- (−) В протоколе нет идемпотентности и replay-гарантий для prompt;
  надежда — на per-harness персистентность сессий (у kimi подтверждена:
  loadSession + resume + fork).

## Альтернативы

- **А: остаться на «вопросы как артефакт» для всех этапов.** Не отклонён,
  а принят как ДЕФОЛТ: нулевая новая сложность, идеальная совместимость с
  D-15, работает на всех harness'ах. Но для плотного диалога (интервью,
  уточнение требований) каждый вопрос — gate-resume-церемония с полным
  рестартом процесса и перезагрузкой контекста: и латентность, и стоимость
  токенов растут линейно от числа вопросов. Зафиксировано как базовый
  режим, а не единственный.
- **Б: ACP как единственный/основной транспорт.** Отклонён: (1) покрытие
  harness'ов неполное — claude/codex только через внешние адаптеры,
  pi — никогда (матрица, риск 9); (2) конфликт с D-15 — живой процесс не
  переживает рестарт, а ядро glamor обязано восстанавливаться из БД после
  любого краха (D-10/ADR-001); (3) контур «процесс на этап» проще,
  предсказуемее и уже покрыт тестами recovery.
- **claude `--input-format stream-json` вместо ACP.** Отклонено как общий
  путь: это per-harness протокол (только claude), тогда как ACP —
  стандарт с растущим покрытием; для claude остаётся внешний ACP-адаптер
  или режим А.
