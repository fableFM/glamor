## P0 — нарушения acceptance

### F-01 (T-14): лента стрима обрезает историю — acceptance не выполнен

Факт: виртуализации нет (`react-virtuoso` отсутствует в
`web/package.json`), а жёсткий `STREAM_BUFFER_CAP = 2000`
(`web/src/stores/streams.ts:5,16-19`) применяется и к REST-догону
(`mergeHistory` → `capped`, `web/src/pages/RunPage.tsx:19-45`,
`stores/streams.ts:31-39`). На ране с 5000+ событий первые ~3000 событий
стадии **молча отбрасываются**. Acceptance T-14: «проверить на ране с
5000+ событий», «исторический ран смотрится так же — вся лента из БД» —
не выполнено и не оговорено в «Итоге» таски.

Как чинить (выбрать и реализовать):
- Виртуализация ленты: `react-virtuoso` (или аналог) для StreamView —
  рендер тысяч событий без cap'а истории; live-cap применять только к
  live-буферу до synced-границы, НЕ к загруженной истории.
- Либо оконная модель: история подгружается страницами назад
  (`GET /runs/{id}/events?before_id=...`) при скролле вверх, cap —
  размер окна, а не отбрасывание начала.
- Добавить vitest на `mergeHistory`/окно с >2000 событий (без потерь,
  дедуп по id сохраняется). Обновить «Итог» T-14: отметить выполнение
  acceptance 5000+ или явно зафиксировать отклонение.

### F-02 (T-16): `run_locked` не показывает занятую ветку (сквозняк не работает)

Факт: фронт читает `details.branch`
(`web/src/components/projects/NewRunForm.tsx:32-35,222-226`), но backend
для `ErrRunLocked` отдаёт голый сентинел без details
(`backend/internal/controller/http/errors.go:29-30`,
`backend/internal/cstmerrors/cstmerrors.go:23`). Пользователь видит
`run_locked: run locked` без имени ветки. «Итог» T-16 заявляет
«run_locked → показ ветки» — по факту не работает.

Как чинить: сервис создания рана при lock-конфликте находит активный ран
по `(project_id, branch)` (запрос уже есть в repo-слое — частичный
UNIQUE-индекс миграции 20260816120000) и возвращает ошибку с
контекстом ветки; контроллер маппит в `details.branch` (и `details.run_id`
заодно). Добавить HTTP-тест: повторный POST /runs на занятую ветку →
409 + `details.branch` в ответе. Обновить «Итог» T-16.

### F-03 (T-16): новые раны не появляются в списках live

Факт: `run.created`-событие не обрабатывается диспатчером
(`web/src/lib/dispatch.ts:35-46`), а `applyStateChanged` игнорирует
неизвестные раны (`web/src/stores/runs.ts:19-25`). Ран, созданный после
загрузки страницы (или другим клиентом — TG-адаптером!), появится в
списке проектов/проекта только после перезагрузки. Acceptance «состояния
списков живые (WS), без ручного рефреша» выполнено частично.

Как чинить: обработать `run.created` в dispatch: инвалидировать/refetch
списка ранов проекта (или upsert минимальной карточки из payload, если
его хватает). Проверить заодно, что бейдж активного рана в списке
проектов обновляется тем же путём.

### F-04 (T-16): `notify_tg` default из настроек проекта не реализован

Факт: в схеме `Project`/`PatchProjectRequest` поля нет вообще
(`web/src/api/schema.d.ts:399-416` — генерится из `api/openapi.yaml`),
форма хардкодит `useState(true)` (`NewRunForm.tsx:52`). Пункт ТЗ T-16
«Настройки проекта: … notify_tg default» не закрыт ни API, ни UI, и это
не оговорено в «Итоге».

Как чинить (полная вертикаль): миграция `projects.+notify_tg_default
INTEGER NOT NULL DEFAULT 1` (goose Go-файл, `AddMigrationContext`, по
образу существующих) → dtorep/репозиторий/маппер → `api/openapi.yaml`
(поле в Project + PatchProjectRequest) → `make gen` → UI: чекбокс в
настройках проекта, дефолт формы из проекта. Альтернатива — явное
отклонение: дописать в T-16 «Итог» и D-73-контекст, что дефолт всегда
«on» (тогда убрать из формы хардкод-претензию настройки). Решение —
пользователя; при отсутствии указания реализовать вертикаль.

## P1 — дефекты и расхождения

### F-05: ноль новых фронт-тестов на T-14/15/16/20

Факт: единственный тестовый файл — `web/src/lib/events.test.ts` (3 теста
WS-клиента из T-13). «vitest 3/3» в саммари технически верно, но покрытие
новых тасок нулевое. При этом тестируемые чистые функции есть:
`stores/streams.ts` (buildBlocks/mergeHistory/cap), `lib/pipelineModel.ts`
(validateSpec/parseSpec/serializeSpec), `lib/format.ts` (slug preview).

Как чинить: добавить vitest как минимум на: (1) mergeHistory/F-01-окно
(>2000 событий, дедуп, порядок); (2) validateSpec — все реализованные
правила + новые из F-08; (3) round-trip parseSpec/serializeSpec
(согласованность с backend-спекой); (4) slug-preview. Не гнаться за
компонентными тестами — только логика.

### F-06 (T-19): маркер доставки двигается ДО отправки оффлайн-сводки

Факт: `backend/internal/notify/telegram/adapter.go:207` (`syncMissed`):
`last_delivered_event_id` обновляется до send сводки; если отправка
упадёт — сводка теряется молча и при рестарте не пересчитается. Это
отдельный ordering-дефект, не покрытый зафиксированным trade-off про
ретраи.

Как чинить: двигать маркер только после успешной отправки сводки
(при фейле — не двигать, следующий старт пересчитает). Добавить тест:
send падает → маркер не сдвинут.

### F-07 (T-17): плейсхолдеры в верхнем регистре не ловятся

Факт: regex `[a-z_]+...` в `backend/internal/service/pipeline/render.go:25`
и `validate.go:78` — `{{Task}}` проходит ValidateSpec и остаётся
литералом в промпте; заявленный fail-fast не срабатывает.

Как чинить: ловить любой `{{...}}` (включая верхний регистр и мусор) и
требовать точного совпадения со списком известных — и в валидации, и в
рендере (один источник regex'а). Тест: `{{Task}}`, `{{ task }}` → ошибка.

### F-08 (T-20): валидация редактора пропускает пустой prompt_template/model

Факт: `web/src/lib/pipelineModel.ts:165-197` не проверяет обязательность
`prompt_template` и `model` — пайплайн с пустым промптом сохранится,
ошибка всплывёт только при ране. ТЗ T-20: «обязательные поля нод
заполнены».

Как чинить: добавить правила (пустой prompt_template, пустой model,
пустой harness — ошибка с подсветкой ноды) + vitest (см. F-05).
Сверить с backend `ValidateSpec`
(`backend/internal/service/pipeline/validate.go`): правила фронта не
должны быть слабее backend.

### F-09 (T-19): telegram-адаптер ходит в repository напрямую — закрепить или развести

Факт: `backend/internal/notify/telegram/adapter.go:15-19` импортирует
`repository/telegram` + read-Queries runs/stages/gates/projects;
read-агрегация `/status` живёт в адаптере (`format.go:199`), а не в
`service/catalog`. Скилл glamor-architecture помещает
`internal/notify/telegram` в «доменные пакеты вне цепочки» и прямо это
не запрещает — но правило не зафиксировано явно, следующий агент
может читать это как прецедент «доменным пакетам можно всё».

Как чинить: (1) read-агрегацию для `/status` перевести на
`service/catalog` (адаптер вызывает service); (2) `repository/telegram`
оставить — это собственная граница хранения домена; (3) дописать в
`.agents/skills/glamor-architecture/SKILL.md` раздел про доменные
пакеты: домен (notify/telegram, daemon, gitx) МОЖЕТ владеть своим
репозиторием состояния, но бизнес-чтения других доменов — через
service. Заодно поправить grep-чек скилла: исключить `*_test.go`
(тесты контроллера легально импортируют repository для сборки).
