## Задачи (по приоритету)

### 1. Скролл стрима при смене стадии

В `web/src/components/run/StagePanel.tsx:176` у `<StreamView>` (внутри —
`<Virtuoso>`) нет `key={stageId}`: компонент не перемонтируется при
переключении стадий, `initialTopMostItemIndex` не пере-применяется,
лента открывается в произвольной позиции вместо конца. Фикс: добавить
`key={stageId}` (или эквивалент). Проверить, что переключение j/k между
стадиями открывает ленту с конца, а прилипание автоскролла
(`followOutput`) не сломано.

### 2. TG live-путь: маркер доставки при фейле send

В `backend/internal/notify/telegram/adapter.go:226-232` (`handleEvent`)
`last_delivered_event_id` двигается defer'ом даже при неудачной
отправке — live-нотификация при сбое сети теряется молча (тот же класс
дефекта, что чинил F-06 в `syncMissed`, `adapter.go:208-212`). Сделать
консистентно: маркер двигать только после успешного send; при фейле —
не двигать (событие доедет через оффлайн-сводку). Осторожно с шиной:
send не должен блокировать Hub надолго — если поэтому defer и
появился, сохрани неблокируемость (например, маркер двигать после
успеха, а при фейле логировать и полагаться на recovery-сводку при
следующем старте/tick). Добавь тест по образцу
`TestOfflineSummaryMarkerNotMovedOnSendFailure`
(`adapter_test.go:538-560`). Обнови «Итог» в
`tasks/T-19-telegram-adapter.md` (датированное дополнение).

### 3. Гонка догона неизвестного рана (фронт)

`web/src/lib/dispatch.ts:31-41,62` (`ensureRunKnown`): второе событие
того же неизвестного рана игнорируется, пока летит первый fetch; если
ответ прочитан до коммита второго перехода — карточка показывает
устаревший стейт до следующего события. Фикс: после завершения fetch
применить отложенные события этого рана (или повторный fetch, если за
время полёта пришли ещё события с id > снапшота). Тест в
`lib/dispatch.test.ts`.
