# T-23 Vendor-память: дельты, FTS5, UI

Статус: todo · M3 · зависимости: T-02 (FTS5-заготовка), T-17 (чтение в M1)

## Цель

Механика роста памяти (D-50): этапы не правят файлы молча, а производят
дельты; ядро применяет; пользователь видит, что память узнала.

## Scope

- **Дельта как артефакт**: этап (standard/deep) пишет
  `vendor-updates/<vendor>.md` (формат секций как в vendors/README.md).
  Ядро после этапа применяет дельту к файлам памяти атомарно (tmp+rename),
  регистрирует в `artifacts` с kind=`vendor_update`.
- **Scope памяти**: запись в локальную (`<repo>/.glamor/vendors/`) — всегда
  auto. В глобальную (`~/.glamor/vendors/`) — по флагу пайплайна:
  `auto` (дефолт) | `gate` (кнопка «принять в глобальную» на финальном
  гейте, diff показан).
- **Summary рана**: секция «что узнала память» — список обновлённых
  вендоров + diff.
- **FTS5-индекс**: содержимое vendor-файлов индексируется (таблица из
  T-02); переиндексация после применения дельты и при старте (dirty-check
  по mtime). Промпт планировщика получает релевантные выдержки (запрос по
  вендорам/терминам из задачи), а не всю память — экономия токенов.
- **Промоушн**: UI-кнопка «в глобальную» на записи локальной памяти.
- **Рекомендация**: `~/.glamor/vendors/` сделать git-репозиторием при
  инициализации (бесплатный аудит/откат); коммиты дельт — простые
  `git add+commit` в этом отдельном репо (не путаем с запретом коммитов в
  проектах пользователя, D-32 — это наша собственная память).
- **UI**: раздел «Память» — дерево вендоров (глобальные/по проектам),
  просмотр, история изменений (из git-лога памяти), правка вручную
  (textarea + сохранить).

## Acceptance

- Ран deep-глубины: дельта применена, видна в summary и в UI памяти.
- FTS5: запрос «kafka idempotency» возвращает релевантный кусок, который
  попадает в промпт планировщика (проверить по prompt-*.md).
- UNVERIFIED-конвенция соблюдена в шаблоне дельты (секция помечается).
