# T-27 Эксперимент: ACP / живое вмешательство

Статус: todo · M4 · зависимости: M1 стабилен, research по ACP

## Цель

Проверить альтернативу модели «вопросы как артефакт» (D-20) для этапов,
где диалог плотный: живой двусторонний протокол вместо ping-pong с
resume.

## Гипотезы к проверке

- `kimi acp` (ACP server over stdio): сессия живёт, вопросы приходят как
  запросы, ответы — без рестарта процесса. Плюсы: мгновенный диалог,
  Interrupt & Steer без убийства процесса. Минусы: процесс живёт часами
  (устойчивость к рестарту демона?), протокол сложнее, поддержка только
  у части harness'ов (kimi, opencode; claude имеет свой вариант через
  `--input-format stream-json`).
- `claude --input-format stream-json` — потоковый ввод: альтернатива ACP
  для claude.

## План эксперимента

1. Spike: ACP-сессия из Go (stdio, JSON-RPC): старт, промпт, получение
   вопроса, ответ, стрим событий. Документировать протокол и подводные
   камни (таймауты, переподключение).
2. Оценка: что даёт vs вариант А по UX и по сложности ядра (recovery!
   живой процесс не переживает рестарт демона — как совместить с D-15?).
3. Решение (ADR-002): остаёмся на А / ACP для выбранных этапов /
   гибрид (этап помечается interactive: true в пайплайне).

## Критерий выхода

- ADR-002 с измеримым сравнением (время ответа на вопрос, код ядра +/-,
  сценарии отказа).
- Если гибрид: пайплайн-нода получает флаг `interactive`, supervisor
  умеет оба режима.
