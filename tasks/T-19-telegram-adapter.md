# T-19 Telegram-адаптер

Статус: done (2026-08-17) · M2 · зависимости: T-04 (шина), T-11 (гейты), T-12 (конфиг)

## Цель

Облегчённый пульт в Telegram (D-70..73): нотификации по этапам, резолв
гейтов, ответы на вопросы, стейт — без стрима вывода harness'а.

## Архитектура

- Модуль `internal/notify/telegram` внутри демона; подписчик in-process
  шины событий (T-04) + клиент внутренних команд ядра (те же пути, что у
  REST). Никаких приватных лазеек в БД.
- Long polling `getUpdates` (без webhook, работает из-за NAT).
  `update_id` = idempotency-key команд (D-12).
- Привязка: `/start` → бот показывает код → пользователь вводит его в UI
  (настройки) → `chat_id` в whitelist (БД или конфиг — в БД, таблица
  `tg_chats`). Чужие чаты игнорируются.
- Токен бота — `~/.glamor/config.yaml`, никогда не логируется, не уходит
  в API-ответах.

## Маппинг событий → сообщения

- `stage.succeeded/failed` → `✅/❌ <stage> · 4m12s · 38k tok` (reply-цепочка
  на «тред» рана: первое сообщение рана — корневое, остальные — reply на
  него; хранить `tg_message_id` корня в `runs`).
- `stage.interrupted/resumed` → `🔁 сеть/сбой, возобновил 2/3`.
- `gate.opened`:
  - `question` → текст вопросов (из questions.md, усечение 3КБ + файл при
    необходимости). Ответ — **reply на это сообщение** (привязка по
    `reply_to_message_id` → gate_id, маппинг в БД).
  - `plan_approval` → краткое саммари spec + inline-кнопки
    [Approve] [Reject]; comment — reply на сообщение.
  - `escalation` → findings + reply для ответа.
  - `final_review` → summary рана + [Принять] [Comment → fix].
- Артефакт по требованию: кнопка «📎 spec.md» → отправка документом
  (лимит TG 50МБ, наш cap 5МБ).

## Команды

- `/status` — компактный стейт всех активных ранов (проект · пайплайн ·
  этап · ожидание). `/stop` — reply на сообщение рана.
- Текст-реплай на любое сообщение рана вне гейта → queue note (D-22).

## Оффлайн и лимиты (D-72)

- Offset последнего доставленного `event_id` в БД; после простоя демона —
  сводка пропущенного ОДНИМ сообщением.
- Напоминание о висящем гейте через N минут (конфиг, дефолт 30).
- Rate limit TG: очередь исходящих с троттлингом (30 msg/s глобально,
  1 msg/s в чат — библиотека или свой лимитер).
- `notify_tg=false` на ране → ран полностью молчит (D-73).

## Acceptance

- E2E с тестовым ботом/моком Bot API (httptest-сервер, интерфейс клиента
  абстрагирован): весь сценарий рана через TG — вопрос→ответ→approve→
  финальный гейт→принять.
- Повторная доставка update (Telegram ретраит) не создаёт дублей.
- Простой демона 10 минут → одна сводка, а не лента.

### Дополнение 2026-08-17 (fix-task-3, п.2 — маркер live-пути)

- **Live-путь (`handleEvent`) приведён к семантике F-06**: раньше
  `last_delivered_event_id` двигался defer'ом даже при неудачной отправке —
  live-нотификация при сбое сети терялась молча. Теперь маркер двигается
  только за учтёнными событиями: успешно отправленными либо не требующими
  отправки (нет маппинга, ран замьючен/не читается, whitelist пуст).
  `handleEvent` возвращает `bool`; при фейле send маркер НЕ двигается,
  senderLoop уходит на пересинхронизацию — событие доедет оффлайн-сводкой
  (D-72).
- **Неблокируемость Hub сохранена**: defer появился не ради асинхронности —
  senderLoop и раньше был синхронным консьюмером (send троттлится
  rateLimiter'ом), сброс медленной подписки обрабатывается resync'ом. Сбой
  send теперь использует тот же механизм resync. Чтобы маркер не
  перепрыгнул через недоставленное событие при следующем успешном send,
  оффлайн-догон (`syncMissed`) обязателен перед live-лентой: при его фейле —
  ретрай с паузой `PollRetryDelay` (защита от горячего цикла при упавшей
  сети), live-события до успешной сводки не обрабатываются.
- Новый тест `TestLiveMarkerNotMovedOnSendFailure`: send падает →
  `handleEvent`=false, маркер не сдвинут, сообщений нет; сеть
  восстановилась → сообщение уходит, маркер догоняет; событие без маппинга
  двигает маркер («учтено») даже при упавшей сети.
- Проверки: build/vet/test -race (пакет telegram) зелёные.

### Дополнение 2026-08-17 (fix-task-2, П.8 — известные ограничения)

Зафиксированные ограничения текущей реализации (код не менялся, факты
проверены по `backend/internal/notify/telegram/`):

- **`rateLimiter.perChat` растёт без очистки** (`adapter.go:346-374`):
  map[int64]time.Time пополняется на каждый отправленный chat_id и не
  чистится. При текущей модели (whitelist привязанных чатов, их единицы)
  утечка несущественна; если чатов станет много — добавить eviction
  (TTL или сброс записей старше chatSpacing).
- **Pending-код привязки один глобальный** (`adapter.go:24-25`,
  `incoming.go:151-162`): `pending_pair_code`/`pending_pair_chat_id` —
  одна пара в state-таблице; второй `/start` (второй пользователь или
  повторный) затирает первый pending. При одновременной привязке двух
  чатов первый не сможет завершить POST /telegram/pair. Осознанное
  упрощение M2 (один оператор); при multi-user — ключ state по chat_id.
